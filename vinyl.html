Personal project · 2026

Ripping vinyl.

Getting records off a turntable and into a 95,000-track music library — which meant building a pipeline between a brand-new laptop and a fourteen-year-old one that refuses to die.

Apple Lossless Two Macs ~290 MB per album 7 seconds end to end

The problem

I have a music library of about 95,000 tracks — roughly a terabyte, assembled over twenty years and consolidated from old iPods, dead hard drives, and a couple of libraries inherited from family. It lives in iTunes. Not Apple Music, not the modern Music app: iTunes, the last version Apple shipped before splitting it apart in 2019.

That matters more than it sounds. A library this size is really a database, and the modern Music app is built around streaming. iTunes is the last piece of Apple software that treats a large collection of files you actually own as the main event. So the library stays where iTunes still runs — on macOS Mojave, which means a machine that can still boot it.

Meanwhile I'd been buying records, and wanted them in the same library as everything else. Which raised the question of how, exactly, a record gets from a turntable into a database on a computer released in 2012.

Two machines, two jobs

The obvious answer was to do everything on the old machine. It has a real analog line-in, it already holds the library, and it's plugged in and running anyway. I tried that first, and it mostly worked — I ripped about ninety albums that way.

But a 2012 laptop is a slow place to do audio work. Declicking a side takes minutes. The recording software fought with the operating system. And doing the fiddly, interactive part of the job — setting track breaks, cleaning up pops, typing in track listings — on a machine that predates the software you're running is an exercise in patience.

So the setup split in two. Capture moves to the new laptop, through a USB audio interface, where the software is fast and the screen is in front of me. The old machine becomes a library server: headless, lid closed, always on, doing nothing but running iTunes and holding a terabyte of music.

Which left the actual problem: moving a finished album from one to the other, reliably, without me having to think about it.

How it works

iTunes has a folder called Automatically Add to iTunes. Drop files in and they get imported and filed by their tags. That's the hook the whole thing hangs on — but it's also the dangerous part, because iTunes watches that folder continuously and will happily import a file that's still being written to it. Half a song, imported and filed, and you won't notice until you play it.

So nothing ever gets written into that folder directly. Instead:

  • Step 1Record the side, split it into tracks, tag it.
  • Step 2Export to a staging folder as Apple Lossless — one folder per album.
  • Step 3A script checks every file before anything moves: is it really lossless, does it have an artist, an album, a title, a track number.
  • Step 4Copy the album across under a temporary name, so an interrupted transfer can never look finished.
  • Step 5Checksum every file on both machines and compare. Only on a perfect match does it get its real name.
  • Step 6One atomic move into the watch folder. iTunes sees a complete album appear, all at once, or nothing at all.

That last step is the whole trick. Because the staging area and the watch folder live on the same disk, moving between them isn't a copy — it's a rename, which the filesystem does instantly and indivisibly. There is no moment where a half-copied album exists in that folder for iTunes to find.

The two laptops are wired together directly rather than going over Wi-Fi, which turns out to be worth about four times the speed: a full album crosses in around three seconds instead of twelve. If that cable is ever unplugged, the script notices and falls back to the network on its own.

What went wrong

The interesting part of any project like this is the gap between the plan and reality. Four things caught me out.

The folder had a different name than it appears to have. The watch folder shows up in Finder as "Automatically Add to iTunes." On disk it's actually called Automatically Add to iTunes.localized — Finder hides the suffix. Every script that used the obvious path failed until I looked at the raw directory listing.

The standard way to read music tags didn't work. macOS has a built-in tool for reading metadata, and it returned nothing at all for the files I'd just exported. The reason is that it reads from the system search index, and a file written thirty seconds ago hasn't been indexed yet. The check meant to catch untagged albums was rejecting every album, including perfectly good ones. I ended up writing a small parser that reads the tags directly out of the file.

A one-character bug rejected everything. I'd written a check to refuse filenames containing a line break — an edge case that would corrupt the verification step. The way I'd written it, the thing I was searching for evaluated to an empty string, and every filename contains an empty string. So the check matched everything and refused every file. Neither of these bugs was visible by reading the code; both showed up the first time it ran against real music.

And the first successful run made fifteen duplicates. Everything worked exactly as designed — the album transferred, verified, imported. It was just an album I'd already ripped three weeks earlier. I'd built guards against the pipeline colliding with itself, and none against the pipeline colliding with the library. Now it asks iTunes whether it already has the album before it sends anything.

Testing it properly

The test I cared about most was the ugly one: what happens if the connection dies halfway through an album.

So I started a 1.4 GB transfer and killed the connection mid-flight. The result was exactly what it should have been — the script stopped and reported failure, nothing reached iTunes, the local copy stayed where it was, and the partial transfer sat on the far side under its temporary name where it couldn't be mistaken for a finished album. Running it again picked up where it left off, re-checked every file, and completed.

That's the difference between a script that works and a script you can trust. The first one works when nothing goes wrong.

The thing I wasn't looking for

While setting this up I checked the backup situation on the machine holding the library, expecting to tick a box. Time Machine was on, it was running hourly, and the library was included. All good.

Except the backup drive held thirteen days of history. A healthy Time Machine keeps daily backups for a month and weekly ones going back further; this one had no weeklies at all. The drive was too small for what it was backing up, so every new backup was quietly deleting an old one to make room. It had been doing that for months.

Nothing was broken, and nothing was lost. But the only copy of a twenty-year library was protected by a safety net less than two weeks deep, and I'd have had no reason to look if I hadn't been building something else. A bigger drive is on its way, and the old one becomes a second copy that lives unplugged.

The lesson I'd actually take from this project isn't about audio. It's that "the backup is running" and "the backup is any good" are different claims, and only one of them is easy to check.

Onto the iPod

There's a reason for the whole arrangement, and it isn't nostalgia. Everything in this library syncs to three iPod Classics — the last iPods Apple made with a hard drive and no network connection at all — and a pair of iPod Touches alongside them.

So a record I rip goes into the library, and from there onto a Classic that plays music and does nothing else. Nothing gets recommended to me. Nothing disappears when a licensing deal expires. An album is where I left it, in the order the artist put it in, and it stays that way whether or not I keep paying anyone.

That's the actual goal. The pipeline exists so that owning music stays as convenient as renting it.

How it was built

I built this with Claude Code, working through it in stages — checking what was actually on the machines first, then the transfer method, then the folder structure, then the script itself — rather than asking for the whole thing at once and hoping.

That order mattered. The slow part was never writing code; it was the things you can only find by looking at the real machines. That the watch folder has a hidden suffix. That the standard tool for reading music tags returns nothing for a file written thirty seconds ago. That my backup drive had been quietly discarding history for months. None of that is guessable from a description of the problem, and all of it would have broken the finished thing.

The bugs were the instructive part. Two of them were in code that read perfectly well — a check that matched every file instead of none, and a path that resolved against the wrong folder. Both were written confidently. Both were caught the first time the thing ran against real music instead of a test file. Which is roughly the lesson: generating the code is the fast part, and deciding what to verify is the actual work.

Where it stands

One command, run from the laptop I record on. It sends everything waiting, refuses anything untagged or already in the library, verifies every file, and tells me what it did. A second command reports whether the whole system is healthy — connection, iTunes, queue, disk space, and how recent the last good backup is.

An album takes about seven seconds to go from finished export to sitting in the library, and I don't have to think about any of the steps in between. Which was the entire point.
