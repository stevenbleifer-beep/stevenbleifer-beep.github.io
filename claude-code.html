Side projects · 2026

Built with Claude Code.

I'm an accountant, not a software engineer. Over the past few months I've used Claude Code to build the things I actually wanted to exist — this site, my study tools, and a handful of stubbornly analog problems involving records, old hard drives, and iPods that predate the App Store.

178 commits Since February 2026 Zero formal training

How I actually use it

The pattern that works for me is not "describe the thing and accept what comes back." It's closer to working with someone competent who has never seen my setup: I say what I want, it looks at what's really there, and it tells me which of my assumptions were wrong before writing anything.

That last part is where most of the value has been. Nearly every project below turned up something I had wrong at the start — a folder that isn't named what it appears to be named, a backup that was running but useless, an iPad that turned out to be a different iPad. None of those were guessable from my description of the problem. All of them would have broken the finished thing.

This site

Everything you're looking at. It started in February 2026 as a single page and is now 178 commits of accumulated tinkering, all hand-rolled — no framework, no build step, no dependencies. Just HTML, one stylesheet, and a bit of JavaScript.

Things it does that aren't obvious from the outside: the changelog generates itself from git history, filtering out the automated commits so only real changes show up. The Library page pulls live from Letterboxd and Goodreads. There's a search box on the home page that indexes every page. And a guestbook runs on a Firebase realtime database with App Check enforced through reCAPTCHA — which sounds tidy written down and took an embarrassingly long debugging session, because Firebase had auto-created a key that didn't appear in any console I could reach and therefore couldn't have domains added to it.

Study tools

The most genuinely useful category, because these were built against real deadlines.

An AUD sprint dashboard for the CPA exam — a day-by-day plan for a two-week run at the Auditing section, with daily simulation and multiple-choice targets weighted toward the units I was weakest in. Checkboxes and counters save to the device, so progress survives closing the tab. It got rearranged more than a dozen times as my actual pace diverged from the plan, which is the honest use case for something like this.

For Accounting Information Systems at Stern, a full set per exam: study guide, practice test, review quiz, key-term flashcards, hardest-questions drill, and exam-style questions — one set for chapters 7, 14 and 19, another for the cybersecurity final on chapter 16 and the CIS Controls.

Separately, for the FAR section, a study guide and a formulas-and-mnemonics sheet built from my own lecture notes and handwritten exam reviews — including the handwritten error logs, which are pure ink and had to be rendered as images to be read at all. Both were written to print cleanly, because the point was to have them on paper.

One thing worth flagging: the notes those were built from stop short of several tested topics, and the study guide says so explicitly rather than quietly filling the gaps. A study tool that pretends to complete coverage it doesn't have is worse than no tool.

Pomodoro

A focus timer, built because every one I tried was either an app I didn't want to install or a website covered in ads.

Configurable focus, short-break and long-break lengths, a long break every n cycles, optional auto-continue between phases, a sound and a browser notification when a phase ends, a label for what you're working on, and a running count of sessions, minutes and cycles. It also holds a wake lock so the screen doesn't sleep mid-session — which was added after the obvious happened.

Ripping vinyl

An automated pipeline that takes a record from a turntable into a 95,000-track iTunes library running on a headless 2012 MacBook Pro — checking the files, verifying every byte across two machines, and importing atomically so iTunes can never catch a half-written album.

It has its own page, including the four bugs that only surfaced against real music and the backup problem I found by accident while building it. Read about the vinyl pipeline →

The music library

The library that pipeline feeds didn't assemble itself. It's about 95,700 tracks, consolidated from old iPods, dead drives, and a second library inherited from family — roughly 168 GB merged in by artist and album, deliberately without importing that library's own database, ratings or play counts, since doing so would have replaced mine rather than added to it.

Consolidating something that size surfaces problems you'd never notice track by track. 1,073 audio files existed on disk with no library entry at all — whole albums, silently absent from the database while sitting right there in the folder. Auditing for that is harder than it sounds: the library's XML escapes ampersands, stores paths in a different Unicode normalisation than the filesystem returns, and is case-inconsistent about folder names. Each of those produced hundreds of false positives before being handled, and one of them would have caused real duplicates if I'd trusted it.

I also built a 500-track "best of 2007–2011" playlist — 33 hours, structured as 25 complete album blocks followed by 200 singles. The interesting problem there was that there is no listening history anywhere in the library, so popularity had to come from an external ranking. And ranking by year tag alone is a trap: remasters, live albums and vinyl reissues carry the reissue's date, so the first pass confidently proposed Bohemian Rhapsody and Highway to Hell as hits of 2009.

Old hard drives

A stack of unlabelled external drives, worked through one at a time to find out what was on them. This started as a hunt for old iOS app files and turned into a small archaeology project.

What they turned out to be: a 500 GB drive with fifteen partitions, no recognisable filesystems, and power-of-two sizes — a PlayStation 4 disk, encrypted against a console motherboard that no longer exists, and therefore permanently unreadable. A High Sierra system drive with no apps but a 53 GB photo library spanning 1980 to 2018. A nearly-empty Windows data partition. A 750 GB FileVault-locked drive that kept dropping off the USB bus and is still unopened.

And one 160 GB drive from an old family PC that had exactly what I was looking for: 49 iOS app files from the right era, every one verified compatible with the device I wanted them on. Along with about 19,000 photos and videos, which are now in a single album rather than scattered across drives nobody could read.

Devices that predate the App Store

The reason for the app hunt. An iPod touch 4, running iOS 6.1.6, jailbroken so it can install software Apple stopped signing over a decade ago.

The same treatment for an iPhone 4S, downgrading from iOS 9 to 6.1.3 — a version Apple still signs, which is what makes it recoverable if it goes wrong. That one is genuinely difficult: the downgrade needs a specific low-level device mode that can only be reached from a jailbroken phone, and getting there means jailbreaking the version you're trying to leave. It's still not finished.

And an iPad I was certain was an iPad 2. It's an iPad 3 — and that distinction decides everything, because the trick that makes the 4S recoverable doesn't exist for the iPad 3. Apple never shipped the release it needs in a form that can still be installed. Being told that before spending an evening on it was worth more than any code.

What I'd tell someone starting

Make it look at your actual setup before it writes anything. Every project here had at least one assumption that was wrong at the start, and finding those first is cheaper than debugging them later.

Ask it to test the failure cases, not the working one. The vinyl pipeline is only trustworthy because we killed a transfer halfway through and watched what it did.

And read what it produces. Two of the bugs in the vinyl project were in code that looked completely reasonable and did the opposite of what it said. Generating code turns out to be the fast part; knowing what to check is the actual work.
